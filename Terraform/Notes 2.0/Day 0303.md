# Terraform and AWS CLI - Day 03 (Part 03): Terraform Provisioners

Welcome to Part 03 of our Day 03 journey! In this final section, we dive into **Terraform Provisioners**. 

Normally, Terraform’s primary role is strict infrastructure provision—meaning it creates the blank slate resources like EC2 instances, S3 buckets, or VPCs. But sometimes, simply creating an empty server isn't enough. After launching an EC2 instance, you might instantly want to update its packages, install a web server, or run some initialization scripts.

This is exactly where provisioners come in. They allow Terraform to execute commands either on your local machine or directly on the remote resource itself. There are two main types:

1. **Local execution (`local-exec`)**: Runs commands on the machine where Terraform is being executed. Useful for tasks like local logging, triggering separate scripts, or writing tracking files.
2. **Remote execution (`remote-exec`)**: Runs commands directly on the provisioned resource (like an EC2 instance). It typically connects using SSH or WinRM and executes commands directly on that machine.

*Note: Although incredibly useful for basic setup and testing, provisioners are considered a last resort in production environments. For complex configurations, dedicated system management tools like Ansible, Puppet, and Chef are far more reliable and scalable.*

## Round 1: The Local Exec Provisioner

I started by creating a new directory named `terraform-provisioner` and populated a `main.tf` file that reused my dynamic S3 bucket code from earlier (relying on `${terraform.workspace}`). However, I paired it with a special Terraform block called a `null_resource`. 

A `null_resource` doesn’t create any real cloud infrastructure; it simply acts as an anchor to trigger a provisioner. I used it to fire a `local-exec` command that writes the newly generated S3 bucket name directly into a local `.txt` file using standard bash redirection (`>>`):

```hcl
# main.tf (local-exec)
resource "aws_s3_bucket" "aws_s3_bucket" {
	bucket = "prashant-${terraform.workspace}-1706"
}

resource "null_resource" "local" {
	provisioner "local-exec" {
		command = "echo s3 bucket created ${aws_s3_bucket.aws_s3_bucket.bucket} >> bucket.txt"
	}
}
```

I ran `terraform init`, followed swiftly by `terraform apply --auto-approve`. The output immediately showed the successful creation of both the bucket and the execution of my local command:

```bash
aws_s3_bucket.aws_s3_bucket: Creating...
aws_s3_bucket.aws_s3_bucket: Creation complete after 7s [id=prashant-default-1706]
null_resource.local: Provisioning with 'local-exec'...
null_resource.local (local-exec): Executing: ["/bin/sh" "-c" "echo s3 bucket created prashant-default-1706 >> bucket.txt"]
null_resource.local: Creation complete after 0s [id=4710514583040045802]
```

To verify, I checked my local directory structure and opened the newly generated `bucket.txt` file. 

```bash
$ cat bucket.txt 
s3 bucket created prashant-default-1706
```

It worked flawlessly! Terraform had successfully bridged the gap between cloud resource creation and a local bash script tracking the output. I tore it all down with `terraform destroy --auto-approve` so I could move onto the main event.

## Round 2: The Remote Exec Provisioner (and a lot of debugging!)

For remote execution, we must provide Terraform with an SSH Key Pair so it can physically log onto the server it creates. I created a dedicated directory `tf-remote` and securely copied over my AWS private key (`tfpractice.pem`).

> **Important Note:** SSH keys require strict file permissions. Before Terraform can use the key, I secured it heavily using `chmod 400 tfpractice.pem` (and later `chmod 600`), ensuring only the owner could read the file. 

I wrote a robust AWS Security Group inside `main.tf` to open up Port 80 (HTTP) for web traffic and Port 22 (SSH) so Terraform could remotely access the instance. I then built out the EC2 `aws_instance` block containing the `remote-exec` provisioner:

```hcl
# main.tf (remote-exec)

resource "aws_security_group" "example_sg" {
	name = "example-security-group"
	description = "Allow HTTP and SSH traffic"
	vpc_id = "vpc-02a8cb96ff4fc044a"

	ingress {
		from_port = 80
		to_port   = 80
		protocol  = "tcp"
		cidr_blocks = ["0.0.0.0/0"]
	}

	ingress {
		from_port = 22
		to_port   = 22
		protocol  = "tcp"
		cidr_blocks = ["0.0.0.0/0"]
	}

	egress { 
		from_port = 0
		to_port   = 0
		protocol  = "-1"
		cidr_blocks = ["0.0.0.0/0"]
	}
}

resource "aws_instance" "web" {
	ami             = "ami-0ec10929233384c7f"
	instance_type   = "t3.micro"
	key_name        = "tfpractice"
	security_groups = [aws_security_group.example_sg.name]

	provisioner "remote-exec" {
		inline = [
			"sudo apt update -y",
			"sudo apt install -y httpd",
			"sudo systemctl enable --now httpd"
		]

		connection {
			type        = "ssh"
			user        = "ec2-user"
			private_key = file("/home/prashant.gohel/terraform/terraform-provisioner/tf-remote/tfpractice.pem")
			host        = self.public_ip
		}
	}
}
```

### The Debugging Gauntlet

Getting this massive block of configuration fully functional was not without aggressive trial and error. Here’s a breakdown of the failures I hacked my way through during validation and apply phases:

**1. The Missing Array Comma:**
I originally defined my `inline` scripts as a block of strings but forgot to separate them with commas. Terraform quickly halted me:
```bash
│ Error: Missing item separator
│ Expected a comma to mark the beginning of the next item.
```

**2. Invalid Arguments in Networking:**
I tried to use `cidr_address = ["0.0.0.0/0"]` inside my security group mappings, which isn't a valid AWS parameter. I quickly caught the error and corrected it to `cidr_blocks`.

**3. The Egress Protocol Crash:**
I originally mapped my outbound egress ports using `from_port = 80` and `to_port = 80` while trying to apply the ALL protocol (`-1`). AWS security layers threw a massive API rejection:
```bash
Error: updating Security Group... from_port (80) and to_port (80) must both be 0 to use the 'ALL' "-1" protocol!
```
I changed both egress ports to `0` and Terraform replaced the security group seamlessly.

**4. The Key Pair vs File Path Confusion:**
My biggest failure happened inside the EC2 resource block right at the end. I initially assigned my local system's absolute file path to the `key_name` variable (`key_name = "/home/prashant.gohel/../tfpractice.pem"`). 

AWS immediately crashed the `apply`:
```bash
│ Error: creating EC2 Instance: ... api error InvalidKeyPair.NotFound: The key pair '/home/.../tfpractice.pem' does not exist
```

**The Epiphany:** The `key_name` argument is NOT looking for a file on my local machine. It expects the name of the Key Pair that *already exists inside the AWS Console*. AWS has absolutely zero access to my local Linux file system! 

The `.pem` file *only* comes into play during the SSH authentication phase inside the **`connection` block**. That is where Terraform executes the command locally, meaning it needs my local key using the `file("path")` function to dial into the cloud. 

Once I corrected the `key_name = "tfpractice"` and properly formatted the `private_key = file("...")` connection flag, the operation worked beautifully. Terraform created the security group, spun up the EC2 instance, utilized my local key to dial in through SSH, installed the `httpd` web server, and enabled the daemon all without a single drop of human intervention!
