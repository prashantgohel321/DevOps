# Terraform and AWS CLI - Day 03 (Part 01)

Welcome to Day 03 of our Terraform journey! Today marks a massive shift in how we think about and structure our Infrastructure as Code. Up until now, we’ve been throwing everything—our provider config, variables, outputs, and all our resources (like S3 and EC2)—into a single directory. While that is perfectly fine for learning the basics or spinning up a test environment, it doesn’t scale. Imagine walking into an enterprise environment where you have to manage 50 VPCs, 200 EC2 instances, and a labyrinth of databases. Trying to manage all of that in one giant file would be a nightmare. To solve this, the industry standard relies on something called Terraform Modules. 

You can think of Terraform modules exactly like functions in a traditional programming language. Instead of writing the exact same block of code every time you want to deploy a server, you write it once as a reusable block (a module) and then "call" it multiple times, passing in different parameters just like function arguments. For example, if you need three different web servers, you just call your web server module three times with different names. It keeps your codebase incredibly clean, modular, and easy to maintain. 

Before we started building our modules today, the first order of business was to clean up our workspace from yesterday. I ran a quick command to take down the EC2 instance we had left running:

```bash
terraform destroy
```

It went through its usual refresh phase, grabbed the state file, asked for confirmation, and systematically dismantled the infrastructure in just under a minute. 

```bash
Plan: 0 to add, 0 to change, 1 to destroy.
...
Do you really want to destroy all resources?
  Enter a value: yes
...
Destroy complete! Resources: 1 destroyed.
```

With the slate clean, I began organizing our project. I created a new directory named `s3_module`, which acts as our dedicated blueprint for creating S3 buckets. Inside this newly minted directory, I created three standard Terraform files: `main.tf`, `variables.tf`, and `outputs.tf`. Yes, modules have the exact same file structure as a regular Terraform project! 

Inside the `s3_module/main.tf` file, I wrote a simple resource block. However, rather than hardcoding the bucket name, I assigned `bucket = var.bucket_name` and set the acl to `"private"`. 

```hcl
# s3_module/main.tf
resource "aws_s3_bucket" "s3_module" {
	bucket = var.bucket_name
	acl = "private"
}
```

This `var.bucket_name` is the secret sauce of reusability. Over in `s3_module/variables.tf`, I declared that `bucket_name` variable with a type of string. This ensures that whenever our main project calls this module, it is forced to provide a bucket name.

```hcl
# s3_module/variables.tf
variable "bucket_name" {
	type = string
}
```

Finally, inside `s3_module/outputs.tf`, I set up an output named `bucket_id`. This effectively tells the module, "Hey, when you finish creating this bucket, hand the unique ID back to whoever called you."

```hcl
# s3_module/outputs.tf
output "bucket_id" {
	value = aws_s3_bucket.s3_module.id
}
```

Now it was time to put our shiny new module to work in our root directory's `main.tf` file. I cleared out the old standalone S3 resource block and replaced it with two module calls, pointing to our local directory path and passing in distinct `bucket_name` values for each. Below the modules, I kept our data block, which filters for the existing security group, and our EC2 instance resource block.

```hcl
# root main.tf
module "s3_bucket1" {
	source = "./s3_module"
	bucket_name = "mys3_bucket1_1001"
}

module "s3_bucket2" {
	source = "./s3_module"
	bucket_name = "mys3_bucket2_1002"
}

data "aws_security_group" "sg" {
	filter {
		name = "group-name"
		values = ["test"] 
	}
}

resource "aws_instance" "ec2" {
	instance_type = "t3.micro"
	ami = "ami-0ec10929233384c7f"

	tags = {
		"name" = "ec2terraform"
	}

	subnet_id = "subnet-09405ef167702efb2"
	security_groups = [ data.aws_security_group.sg.id ]
}
```

Of course, no major refactoring goes without a few hiccups. My first attempt to validate the code immediately stopped in its tracks:

```bash
$ terraform validate
╷
│ Error: Module not installed
│ 
│   on main.tf line 5:
│    5: module "s3_bucket1" {
│ 
│ This module is not yet installed. Run "terraform init" to install...
```

This was a great "Aha!" moment. Terraform doesn't just magically scan your folders; whenever you introduce a new module (even a local one), you must instruct Terraform to process and initialize that modular structure:

```bash
$ terraform init
Initializing the backend...
Initializing modules...
- s3_bucket1 in s3_module
- s3_bucket2 in s3_module
...
Terraform has been successfully initialized!
```

After initializing, I ran `terraform validate` again, hoping for a green light. Instead, I was hit with an "Invalid reference" error from `s3_module/main.tf` because I had accidentally typed `acl = private` without quotes. Once I added the quotes around `"private"`, I naturally ran into another snag regarding the `outputs.tf` file located in the root directory. 

```bash
│ Error: Unsupported attribute
│ 
│   on outputs.tf line 9, in output "s3_bucket1":
│    9: 	value = module.s3_bucket1.bucket_name
│ 
│ This object does not have an attribute named "bucket_name".
```

This highlighted how modules encapsulate data. The root directory cannot just reach into the module and grab the variable that was passed in (`bucket_name`). It can ONLY see what the module explicitly outputs (`bucket_id`). I updated my root `outputs.tf` file to properly reference `module.s3_bucket1.bucket_id`.

```hcl
# root outputs.tf
output "aws_s3_bucket1" {
	value = module.s3_bucket1.bucket_id
}

output "aws_s3_bucket2" {
	value = module.s3_bucket2.bucket_id
}

output "sg" {
	value = data.aws_security_group.sg.id
}

output "ec2" {
	value = aws_instance.ec2.public_ip
}
```

With that logical disconnect fixed, `terraform validate` finally rewarded me with a "Success!" message. Feeling confident, I initiated `terraform apply --auto-approve`. 

The operation spun up the EC2 instance flawlessly but spectacularly crashed during the S3 bucket creation phase:

```bash
│ Error: creating S3 Bucket (mys3_bucket2_1002): operation error S3: CreateBucket, https response error StatusCode: 400 ... api error InvalidBucketName: The specified bucket is not valid.
```

The culprit? I had named my buckets with underscores. AWS S3 bucket naming conventions strictly prohibit underscores! To fix this, I hopped back into the root `main.tf` and renamed the module inputs to `mys3bucket11001` and `mys3bucket21002` to make them DNS-compliant. 

When I pushed the corrected code again, Terraform demonstrated its state management brilliance. It destroyed and recreated the EC2 instance tied to the failed run while successfully building the two appropriately named S3 buckets in parallel.

```bash
Apply complete! Resources: 3 added, 0 changed, 1 destroyed.

Outputs:
aws_s3_bucket1 = "mys3bucket11001"
aws_s3_bucket2 = "mys3bucket21002"
ec2 = "52.202.159.96"
sg = "sg-041bb8645e6e980f0"
```

To wrap up this incredible session, I took the time to review the theoretical underpinnings of our project foundation, entirely defined inside `provider.tf`. 

```hcl
# root provider.tf
terraform {
	required_providers {
		aws = {
			source = "hashicorp/aws" 
			version = "~>5.0" 
		}
	}
}

provider "aws"  { 
	region = var.region_name
}
```

The `required_providers` block guarantees that anyone picking up our code will have the exact same starting environment plugins (from the public registry at `registry.terraform.io`). All of these downloads get stashed locally in the `.terraform` directory when we run `terraform init`.

Today we learned how to architect reusable infrastructure with Modules, debug variable limits, fix naming failures mid-flight, and prove everything clicks together perfectly when returning output values back up the chain!
