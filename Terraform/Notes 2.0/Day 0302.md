# Terraform and AWS CLI - Day 03 (Part 02): Terraform Workspaces

Welcome to Part 02 of our Day 03 journey! After mastering modules, we moved right into another critical concept for managing real-world infrastructure: **Terraform Workspaces**. 

In a real enterprise project, you almost never have just one environment. You usually have a development environment (dev) for testing new features, a staging environment for pre-production validation, and a production environment (prod) where the live system actually runs. Each of these environments often requires similar infrastructure—like VPCs, EC2 instances, or S3 buckets—but they must remain completely isolated from each other. 

If you use a single state file to manage all of these environments, there is a massive risk of accidentally applying unstable development changes directly to production, which breaks things. This is where Terraform Workspaces save the day. A workspace in Terraform is essentially a completely separate, isolated state file. By having a separate state file for dev, staging, and prod, Terraform can safely manage each environment independently while reusing the exact same configuration code! 

Before getting into the code, I engaged in a bit of a battle with Linux directory management. I wanted to structure my notes and experiments perfectly, but I ran into a flurry of copy and removal errors:

```bash
mkdir: cannot create directory ‘0302’: File exists
cp: cannot copy a directory, '../Notes', into itself, '0302/Notes'
rmdir: failed to remove 'Notes/0302': Directory not empty
rmdir: invalid option -- 'r'
```

Eventually, I wrestled the file system into submission using `rm -rf Notes/0302/` and successfully created a clean, dedicated directory for this session named `tf-workspace-lab`. 

With my new lab directory ready, the first thing I checked was my current active workspace:

```bash
$ terraform workspace list
* default
```

By default, Terraform always places you in a workspace called `default`. Everything we build starts here unless we specify otherwise! 

Next up, I needed to make sure I didn't hit any AWS bucket limit errors. I reviewed my history and used the AWS CLI to manually force-delete the buckets we had created in Part 01:

```bash
$ aws s3 rb s3://mys3bucket11001 --force
remove_bucket: mys3bucket11001

$ aws s3 rb s3://mys3bucket21002 --force
remove_bucket: mys3bucket21002

$ aws s3 rb s3://prashantgohel1706 --force
remove_bucket: prashantgohel1706
```

With the cloud cleaned up, I copied over the provider configuration and defined a simple S3 bucket resource block in our new `main.tf`. The true magic of workspaces lies in how we constructed the bucket name:

```hcl
# main.tf
terraform {
	required_providers {
		aws = {
			source = "hashicorp/aws"
			version = "~>5.0" 
		}
	}
}

provider "aws"  { 
	region = "us-east-1"
}

resource "aws_s3_bucket" "aws_s3_bucket" {
	bucket = "prashant-${terraform.workspace}-1706"
}
```

Notice the special variable `${terraform.workspace}` embedded right in the bucket name! Terraform automatically injects the name of the active workspace into this variable during execution. This means our bucket name will dynamically adapt based on which environment (dev, staging, or prod) we are currently sitting in! 

Since I had just moved files around, I naturally forgot to initialize the directory and was hit with an error when trying to run `terraform validate`:

```bash
│ Error: Missing required provider
│ 
│ This configuration requires provider registry.terraform.io/hashicorp/aws...
```

I quickly ran `terraform init`, which downloaded our AWS plugins and locked the dependencies. 

It was time to create our environments. I used the `terraform workspace new` command to spin up my development workspace:

```bash
$ terraform workspace new dev
Created and switched to workspace "dev"!

You're now on a new, empty workspace. Workspaces isolate their state...
```

I checked my directory tree right after this, and I noticed something awesome: Terraform had automatically generated a hidden directory structure internally to separate my states!

```bash
$ tree
.
├── main.tf
└── terraform.tfstate.d
    └── dev
```

I systematically created two more workspaces using `terraform workspace new staging` and `terraform workspace new prod`. Looking at my environment list confirmed I had everything structured perfectly:

```bash
$ terraform workspace list
  default
  dev
* prod
  staging
```

I switched exactly into the `dev` environment using `terraform workspace select dev` and fired off a `terraform apply --auto-approve`. It successfully created the bucket explicitly tagged with `dev`:

```bash
aws_s3_bucket.aws_s3_bucket: Creating...
aws_s3_bucket.aws_s3_bucket: Creation complete after 7s [id=prashant-dev-1706]
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
```

I then switched over to `staging` using `terraform workspace select staging` and applied the exact same code block. Because of the dynamic `${terraform.workspace}` variable and isolated state file, Terraform created a uniquely named bucket perfectly tailored for staging:

```bash
aws_s3_bucket.aws_s3_bucket: Creation complete after 6s [id=prashant-staging-1706]
```

And finally, I jumped into `prod` and repeated the operation:

```bash
aws_s3_bucket.aws_s3_bucket: Creation complete after 6s [id=prashant-prod-1706]
```

To prove everything worked completely isolated from one another, I checked my AWS layer using the CLI, and there they all were—three distinct environments spawned from a single Terraform configuration file:

```bash
$ aws s3 ls
2026-04-14 12:05:36 prashant-dev-1706
2026-04-14 13:36:05 prashant-prod-1706
2026-04-14 13:35:04 prashant-staging-1706
```

Because leaving resources running wastes money, I systematically burned it all down. Starting in `prod`, I ran `terraform destroy --auto-approve`. Then, I switched to `dev` and destroyed it. Finally, I switched to `staging` and erased that infrastructure too. The state structures correctly tracked the destruction within their respective boundaries independent of one another.

Once the cloud was stripped bare, I cleaned up the local workspaces to leave the environment completely pristine: 

```bash
$ terraform workspace delete staging
Deleted workspace "staging"!

$ terraform workspace delete prod
Deleted workspace "prod"!

$ terraform workspace select default
Switched to workspace "default".

$ terraform workspace delete dev
Deleted workspace "dev"!
```

Checking my final root configuration, I was cleanly back at `default` with my isolated state directory completely purged. 

```bash
$ tree
.
├── main.tf
└── terraform.tfstate.d

1 directory, 1 file
```

We successfully demonstrated how to reuse code safely, preventing dev, staging, and prod from spectacularly destroying each other!
