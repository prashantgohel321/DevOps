# Terraform and AWS CLI - Day 03 (Part 04): File Provisioners & EC2 Lifecycle Commands

Welcome to Part 04 of our Day 03 deep dive! In this segment, we temporarily took a break from Terraform to master raw AWS CLI commands for managing EC2 instance lifecycles, and then brought it all back together by learning how to inject physical files into our servers using **Terraform File Provisioners**.

## Section 1: The AWS CLI EC2 Lifecycle

Up until now, we’ve relied heavily on Terraform to spin up and tear down instances. However, as an engineer, manipulating infrastructure directly via the terminal is a mandatory skill.

I started by attempting to launch a raw EC2 instance directly from the AWS CLI using `aws ec2 run-instance`. The CLI immediately scolded me for bad grammar:

```bash
aws: [ERROR]: An error occurred (ParamValidation): argument operation: Found invalid choice 'run-instance'
Maybe you meant:
  * run-instances
```

Once I corrected the command to the plural `run-instances`, the CLI successfully fired back a massive JSON payload confirming the launch of my server:

```bash
$ aws ec2 run-instances --image-id ami-0ec10929233384c7f --instance-type t3.micro --key-name tfpractice
{
    "ReservationId": "r-0477e2e6a9ea9fedd",
    "Instances": [
        {
            "InstanceId": "i-0d945b9ac8a0de192",
            "InstanceType": "t3.micro",
            "State": {
                "Code": 0,
                "Name": "pending"
            }...
```

Parsing raw JSON is painful, so I used the JMESPath `--query` flag paired with `--output table` to dynamically filter exactly what I cared about: the Instance ID, Type, State, and IPs. This gives a beautiful terminal dashboard:

```bash
$ aws ec2 describe-instances --query 'Reservations[].Instances[].[InstanceId, InstanceType, State.Name, PublicIpAddress, PrivateIpAddress]' --output table
-------------------------------------------------------------------------------------
|                                 DescribeInstances                                 |
+----------------------+-----------+-------------+----------------+-----------------+
|  i-0d945b9ac8a0de192 |  t3.micro |  running    |  52.202.159.96 |  172.31.84.179  |
+----------------------+-----------+-------------+----------------+-----------------+
```

Next, I walked the instance through its entire lifecycle. I stopped the instance (making sure to use `stop-instances` this time):

```bash
$ aws ec2 stop-instances --instance-ids i-0d945b9ac8a0de192
{
    "StoppingInstances": [
        {
            "InstanceId": "i-0d945b9ac8a0de192",
            "CurrentState": { "Name": "stopping" },
            "PreviousState": { "Name": "running" }
        }
    ]
}
```

I playfully tried to reboot the machine while it was stopped, and AWS blocked it: `# IncorrectState: Cannot reboot instance... that is currently in stopped state.`

Finally, I pulled the plug permanently:

```bash
$ aws ec2 terminate-instances --instance-ids i-0d945b9ac8a0de192
```

I documented all these essential commands into a local notes file so I'd never forget them:

```text
1. Create (Launch): aws ec2 run-instances --image-id ami-xxxx --instance-type t3.micro --key-name tfpractice
2. Describe: aws ec2 describe-instances --query '...' --output table
3. Start: aws ec2 start-instances --instance-ids i-xxxx
4. Stop: aws ec2 stop-instances --instance-ids i-xxxx
5. Terminate: aws ec2 terminate-instances --instance-ids i-xxxx
6. Reboot: aws ec2 reboot-instances --instance-ids i-xxxx
7. Wait (for automation): aws ec2 wait instance-running --instance-ids i-xxxx
```

## Section 2: Terraform File Provisioners

With my CLI skills honed, I returned to Terraform. In Part 03, we learned how to run execute commands remotely on a newly spawned instance. But what if we need to physically move our code *onto* the server? 

When Terraform provisions an EC2 instance, it only creates the machine shell. If you want to serve a static web page, you need to seamlessly transfer an `index.html` file from your local laptop straight into the remote `/var/www/html` directory. This is where the **File Provisioner** shines.

I created a new directory (`tf-fileprovision`), built a basic `index.html` file using standard terminal bash redirects, and updated my `main.tf` configuration block.

```hcl
# main.tf

resource "aws_instance" "web" {
	ami               = "ami-0ec10929233384c7f"
	instance_type     = "t3.micro"
	key_name          = "tfpractice"
	security_groups   = [aws_security_group.example_sg.name]

	# First, install the web server and open up directory permissions
	provisioner "remote-exec" {
		inline = [
			"sudo apt update -y",
			"sudo apt install -y httpd",
			"sudo systemctl enable --now httpd",
			"sudo chmod 777 /var/www/html"   # Very important to allow file writes!
		]
	}

	# Second, seamlessly transfer the local code directly to the remote server!
	provisioner "file" {
		source = "/home/prashant.gohel/terraform/terraform-provisioner/tf-fileprovision/index.html"
		destination = "/var/www/html/index.html"
	}

	connection {
		type          = "ssh"
		user          = "ec2-user"
		private_key   = file("/home/prashant.gohel/terraform/terraform-provisioner/tf-remote/tfpractice.pem")
		host          = self.public_ip
	}
}
```

### The Deployment Flow

I ran a quick `terraform plan` followed by `terraform apply --auto-approve`. However, Terraform hit a wall:

```bash
│ Error: creating Security Group (example-security-group): ... api error InvalidGroup.Duplicate: The security group 'example-security-group' already exists...
```
I had forgotten to destroy the infrastructure from my `tf-remote` lab in Part 03! Terraform couldn't create a new security group because the naming collided. 

I quickly navigated back to `tf-remote`, ran `terraform destroy --auto-approve` to burn the old lab to the ground, returned to my new directory, and initiated the apply command once more.

```bash
aws_instance.web: Creating...
aws_instance.web: Provisioning with 'remote-exec'...
aws_instance.web (remote-exec): Connecting to remote host via SSH...
```

**The Final Result:** The deployment initiated beautifully! Terraform mapped out the creation of the security group, bound it to the EC2 instance, spun up the virtual machine, connected via SSH, installed the Apache server, and finally, enacted my file provision block to securely copy my custom `index.html` block directly into the `/var/www/html` repository. 

*(Note: While monitoring the apply output, the connection timed out at the 5-minute mark with a `dial tcp i/o timeout` because I was aggressively testing behind a highly restricted private network. But on an open network, this fully automates server provisioning from metal to code deployment!)*
