## **Understanding File Movement, Execution Control, and Hidden Behaviors That Affect Real Builds**

- Now the filesystem is already being built step by step in your mind, so from here the focus shifts to the instructions that look simple on the surface but have deeper behavior internally, especially in real projects where builds become slow, images become large, or containers behave unexpectedly.

## **COPY vs ADD — Same Goal, Different Internal Behavior**

**You already used:**

```dockerfile
COPY . .
```

- At first glance, both **`COPY`** and **`ADD`** seem to do the same job: move files into the image. But internally they behave differently, and that difference matters in production.

- **`COPY`** is straightforward. It takes files from your local build context and places them into the image filesystem. Nothing extra happens. No interpretation, no transformation. This predictability is why it is preferred.

- **`ADD`**, on the other hand, has additional logic built into it. If you give it a compressed archive like `.tar.gz`, it automatically extracts it. If you give it a URL, it can even download the file during build. That sounds powerful, but this “smart behavior” is exactly what makes it risky, because now the same instruction can behave differently depending on input type.

**Example:**

```dockerfile
ADD app.tar.gz /app
```

- **Here, instead of copying `app.tar.gz`, Docker extracts it into `/app`. Internally, this means the layer will contain extracted files, not the archive itself.**

- Because of this implicit behavior, debugging becomes harder and caching becomes less predictable. That’s why in real DevOps workflows, **`COPY`** is used almost everywhere, and **`ADD`** is only used when you intentionally need auto-extraction.

## **Build Context — What Actually Gets Sent to Docker**

**When you run:**

```bash
docker build .
```

- Docker does something many people don’t realize. It does not directly read files from your system during each **`COPY`**. Instead, it first creates a snapshot of your current directory and sends it to the Docker daemon as a package. This package is called the build context.

**So if your project folder contains:**

```bash
project/
 ├── app.js
 ├── node_modules/
 ├── .git/
 ├── logs/
```

- Everything gets sent unless explicitly ignored.

- That means even if you don’t COPY `node_modules`, it still travels to Docker, increasing build time significantly.

- This is where `.dockerignore` becomes critical.

## **.dockerignore — Controlling What Enters the Build**

- A `.dockerignore` file works exactly like `.gitignore`, but for Docker builds.

Example:

```bash
node_modules
.git
*.log
```

**Now when Docker prepares the build context, it excludes these files. This directly reduces:**

* build time (less data transfer)
* image size (if accidentally copied)
* cache invalidation (fewer file changes to track)

Internally, this also affects caching because Docker calculates checksums of files to decide whether a COPY layer is still valid. If unnecessary files are included, even small changes can invalidate cache.

## **ENTRYPOINT vs CMD — How Container Execution Really Works**

This is one of the most misunderstood parts.

**You already saw:**

```dockerfile
CMD ["bash"]
```

CMD defines a default command, but it is replaceable.

**Now introduce ENTRYPOINT:**

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

**Internally, Docker combines them like this:**

```bash
ENTRYPOINT + CMD = final command
```

**So container runs:**

```bash
python app.py
```

**Now if you override:**

```bash
docker run image test.py
```

> Docker replaces CMD only, not ENTRYPOINT. So execution becomes:

```bash
python test.py
```

- This means **`ENTRYPOINT`** is the fixed executable, and **`CMD`** is just default arguments.

**If instead you only use CMD:**

```dockerfile
CMD ["python", "app.py"]
```

**Then overriding replaces the entire command:**

```bash
docker run image ls
```

- Now `ls` runs, not python.

- Internally, Docker stores both ENTRYPOINT and CMD in image configuration, and at runtime it merges them before starting the container process.

## **USER — Changing Who Runs Inside the Container**

By default, containers run as root. That means any process inside has full privileges.

```dockerfile
USER appuser
```

- This changes the execution user for all following instructions and also for the container runtime.

**Internally, Docker does not create the user automatically. You must create it using something like:**

```dockerfile
RUN useradd -m appuser
USER appuser
```

- When the container starts, Docker sets the process UID (user ID) to this user instead of root.

**This is important because:**

* limits damage if app is compromised
* avoids permission issues when mounting volumes
* follows production security practices

## **VOLUME — Separating Data From Image Layers**

```dockerfile
VOLUME /data
```

- This declares that `/data` should not be stored inside the image layers. Instead, it should be managed separately as a volume.

**Internally, when a container starts:**

* Docker creates a volume (if not provided)
* mounts it into `/data`
* anything written there bypasses image layers

This is important because image layers are read-only, and containers use a thin writable layer on top. Volumes skip that and directly store data outside, making it persistent even if the container is deleted.

One subtle but important behavior is that if your image already has files inside `/data`, and you mount a volume there, those files become hidden because the volume overlays that path.

Here overlays means the volume takes precedence over the image content at that path, effectively hiding it. This can lead to confusion if you expect certain files to be present but they are not visible due to the volume mount.

## **SHELL — Changing How RUN Commands Execute**

**By default, Docker uses:**

```bash
/bin/sh -c
```

for **`RUN`** instructions.

**If you write:**

```dockerfile
RUN echo hello
```

**It actually runs:**

```bash
/bin/sh -c "echo hello"
```

**Now if you change shell:**

```dockerfile
SHELL ["/bin/bash", "-c"]
```

- All future RUN commands use bash instead.

**This matters when you rely on bash-specific features like:**

* `[[ condition ]]`
* advanced scripting
* pipefail behavior

Internally, Docker just updates the execution configuration for future RUN steps.

## **HEALTHCHECK — Continuous Monitoring of Container State**

```dockerfile
HEALTHCHECK CMD curl -f http://localhost:8080 || exit 1
```

- This tells Docker to periodically run this command inside the container.

- If the command succeeds, container is marked healthy. If it fails, it becomes unhealthy.

**Internally:**

* Docker runs this command in intervals
* tracks exit codes
* updates container status

**You can see it with:**

```bash
docker ps
```

This becomes important in orchestration systems like Kubernetes, where unhealthy containers are restarted automatically.

## **ONBUILD — Delayed Execution for Child Images**

```dockerfile
ONBUILD COPY . /app
```

- This instruction does nothing during the current build.

- Instead, it gets stored in the image metadata. When another Dockerfile uses this image as a base, this instruction is triggered automatically.

**So if someone writes:**

```dockerfile
FROM your-image
```

- Then **`ONBUILD`** instructions execute in that new build.

- Internally, Docker stores **`ONBUILD`** triggers and injects them into the next build process.

- This is mostly used in base images designed for automation, but it can also cause confusion if not documented properly.

## **Cache Behavior — How One Change Affects Everything Below**

Docker caching is not random. It works like a chain.

**For each instruction, Docker checks:**

* instruction text
* input files (for COPY)
* environment

- If all match a previous build, it reuses that layer.

- But the moment one layer changes, all layers after it must rebuild.

**Example:**

```dockerfile
RUN apt update
COPY . .
RUN npm install
```

**If any file changes:**

* **`COPY`** layer invalidates
* **`npm install`** runs again

- Even if dependencies didn’t change.

- This is why ordering matters. You always want stable steps first, changing steps later.

## **What Is Now Clear Internally**

**At this stage, Dockerfile is no longer just instructions. It is a controlled system where:**

* files enter through build context
* instructions modify filesystem or metadata
* execution behavior is defined through CMD/ENTRYPOINT
* runtime behavior is influenced by USER, ENV, VOLUME
* caching depends heavily on order and input changes

And most importantly, every instruction leaves a permanent trace as a layer.
